## 1. Context

The portal was written to run as **one gunicorn worker with threads**. That was a deliberate simplification
(decision 10 of the [history](../history.md)), and it shows in where the portal keeps its state.

**Files in the `resolver-portal-config` volume** (`/app/config`), each written atomically under an advisory
file lock:

| File | Module | Holds |
|---|---|---|
| `users.json` | `portal/users.py` | accounts: password hash, role, GS1 Company Prefixes, disabled, must change password, created, last sign-in |
| `records-meta.json` | `portal/meta.py` | who created and who last changed each record, and when |
| `journal.jsonl` | `portal/journal.py` | history and audit trail: sign-ins, user administration, every record change with the record's full content |
| `secret.key` | `portal/app.py` | the key that signs session cookies, when `PORTAL_SECRET_KEY` is not set |

**Memory of the single worker process** (`portal/app.py`, `portal/linkcheck.py`):

| State | Lifetime | Used for |
|---|---|---|
| `LoginThrottle` | 15 minutes | five failed sign-ins lock a user name or an address |
| `IMPORTS` | 30 minutes | a previewed spreadsheet import (the plan) and, once applied, its progress and results |
| `LINK_JOBS` | 30 minutes | progress and results of a link check over many records |
| `LAST_FULL_CHECK` | until restart | the result of the latest "check every record", shown in the record list |
| `linkcheck._cache` | 10 minutes | the result of checking one address, so that a site is not asked twice |

Imports and link checks run in **threads of the web process**. The journal is read by scanning the whole
file. The portal is deliberately given **no MongoDB credentials**: `docker-compose.yml` blanks `MONGO_URI`
for it and it talks to the data entry API only.

Consequences today:
- a second portal replica would have its own sign-in lockout, would not see an import previewed on the other
  replica, and would answer "expired" to a browser polling a job it does not hold;
- a restart loses running imports and link checks;
- the journal grows without limit and every history or audit query reads all of it;
- items 2.4 (tenants), 4.1 (log of resolver requests) and 7.4 (load test) need state that several processes
  share.

The official services were not written for this either: `web-service` and `data-entry-service` run Flask's
built-in server (`python -m main` → `app.run()`), and every service in `docker-compose.yml` has a fixed
`container_name`, which Compose refuses to scale.

## 2. Decision

1. **A database of the portal's own** — `resolver_portal` — in the existing MongoDB, reached with **a user
   of its own** that has `readWrite` on that database only. The official database `resolver_ce` and its
   collections are not touched; the portal still writes records through the data entry API, never directly.
   The portal never receives the root credentials.
2. **Background jobs in a collection, run by a worker container.** Imports and link checks become documents
   in `jobs`; a `portal-worker` service (the portal's image with another command) claims them one at a time.
   No new infrastructure. The web process only queues jobs and reads their progress.
3. **Short-lived state in collections that MongoDB empties itself** (TTL indexes): sign-in failures, import
   previews and job results, the link checker's cache.
4. **The session key in `.env`** (`PORTAL_SECRET_KEY`), generated by the installer like the other secrets
   and shared by every replica. The `secret.key` file stays as a fallback for an installation with one
   portal replica and no key in `.env`.
5. **Journal retention by age, per category**, configured in `.env` and applied by MongoDB (TTL):
   sign-in events 180 days by default; record versions and administration kept for ever by default.
6. **Automatic migration at start-up**: when the portal's collections are empty and the old files exist, the
   portal imports them once and renames them `*.migrated`; they stay in the volume as a copy.
7. **Tests**: the existing test programs use `mongomock` and keep running without Docker or MongoDB; a new
   CI job runs the storage tests against a real `mongo:7` service container.
8. **Four deliveries**, each with its own bundle and staging check (section 7).

## 3. Design

### 3.1 Database, user and connection

- Database `resolver_portal` (`PORTAL_DB_NAME`), user `resolver_portal` (`PORTAL_DB_USERNAME`), password
  `PORTAL_DB_PASSWORD`. `.env.example` carries development defaults, as for the other secrets; the installer
  writes random values to `.env`.
- The user is created by **a one-shot Compose service, `portal-db-init`**: the portal's image running
  `portal/db_init.py`. It receives the root `MONGO_URI` (as the official services already do), creates the
  user, or updates its password and roles when it exists, and exits. Python in the portal's image, rather
  than a `mongosh` script in the database image, lets the development tests run the same script against a
  real MongoDB in CI. `portal-service` and
  `portal-worker` depend on it with `condition: service_completed_successfully`. Every way of starting the
  stack (installer, manual `docker compose up -d`, a restore) therefore ends with the right user and
  password, and changing `PORTAL_DB_PASSWORD` in `.env` takes effect at the next `up -d`.
  (MongoDB's own `/docker-entrypoint-initdb.d` scripts run only on an empty volume, so they cannot serve
  existing installations.)
- The portal builds its connection from these variables and `PORTAL_DB_HOST` (default
  `database-service:27017`), with `authSource=resolver_portal`. `MONGO_URI` stays blank for the portal.
- `portal/store.py` holds the client (one per process, `pymongo` connection pool), creates the indexes at
  start-up and gives the other modules their collections. The public functions of `users.py`, `meta.py` and
  `journal.py` keep their names and results, so `app.py` changes little.

### 3.2 Collections

| Collection | `_id` | Fields | Indexes |
|---|---|---|---|
| `users` | user name | `hash`, `role`, `prefixes`, `disabled`, `mustChange`, `created`, `lastLogin` | — |
| `record_meta` | record key (`meta.key()`) | `createdAt`, `createdBy`, `updatedAt`, `updatedBy` | — |
| `journal` | ObjectId (`jsonl-<line>` when migrated) | `at` (date), `user`, `action`, `category`, `anchor`, `qpath`, `doc`, `detail`, `expiresAt` | `{at: -1}`; `{anchor, qpath, at: -1}`; `{user, at: -1}`; `{category}`; TTL on `expiresAt` |
| `login_failures` | ObjectId | `key` (user name or address), `at` (date) | `{key, at}`; TTL on `at`, 15 minutes |
| `jobs` | token | `type` (`import`, `linkcheck`), `user`, `state`, `created`, `queuedAt`, `startedAt`, `finishedAt`, `heartbeat`, `worker`, `attempts`, `done`, `total`, `error`, `expiresAt`; imports `plan`, `keyRecords`, `results`; link checks `scope`, `urls`, `problems`, `records` | `{state, created}`; TTL on `expiresAt` |
| `workers` (step 3) | worker name (`host:pid:mode`) | `seen`, `mode`, `job` | TTL on `seen`, 10 minutes |
| `linkcheck_cache` | address | `result`, `expiresAt` | TTL on `expiresAt` |
| `settings` | name | `value` (`lastFullCheck`, `journalRetention`, `migration`); lock documents `lock:<name>` | — |

Notes:
- **Last active administrator**: `users.update()` and `users.remove()` keep their rule. A standalone MongoDB
  has no multi-document transactions, so every change of users runs under a lock shared by all processes (a
  document `lock:users` in `settings`, created with a unique `_id`; one left by a process that died is broken
  after a minute): two administrators acting at the same moment cannot both remove the last one.
- **Dates**: stored as BSON dates (TTL needs them); the API still returns ISO 8601 strings with a `Z`, so the
  browser sees no change.
- **Size**: a document holds at most 16 MB. An import is limited to 5,000 rows and 700 KB
  (`sheet.FORMATS`), so its plan and results fit in one job document.
- **`create_user.py`** keeps its command line and writes through the same store.

### 3.3 Jobs and the worker

- **States**: `prepared` (an import preview, waiting for *Apply*) → `queued` → `running` → `finished` or
  `failed`. A link check starts at `queued`.
- **Claim**: the worker takes the oldest `queued` job with `find_one_and_update`, sets `running`, its own
  name and a `heartbeat`, and renews the heartbeat while it works. Two workers can never take the same job.
- **A worker that dies**: a `running` job whose heartbeat is older than two minutes goes back to `queued`
  and continues from `done` (each record of an import is a separate, repeatable write to the data entry API).
- **Polling**: the worker looks for work every second when idle. Change streams would avoid that, but they
  need a replica set; the single MongoDB of a standard installation has none.
- **Expiry**: `expiresAt` = 30 minutes after the preview or after the end of the job, as today.
- **Scale**: one job at a time per worker; more workers give more parallel jobs. The link checker keeps its
  eight threads inside a job.

**As implemented in step 3** (the owner's choices on the open points, all as recommended, and details the
implementation added):
- **Where jobs run**: `PORTAL_WORKER=external` (default) — the `portal-worker` service, the portal's image
  running `python worker.py`, always present in `docker-compose.yml`; `embedded` — a worker thread inside the
  portal process, for the development tests and a set-up without that service. One worker by default; its
  replicas are decided with the others in step 4. No cancel button for now (a later backlog item).
- **An interrupted import continues** from the first record not written. After three claims of the same job
  (`attempts`) a silent worker's job fails with `job.interrupted` instead of going back to the queue, so a job
  that kills its worker cannot loop for ever; what was written stays. **A link check starts again** from the
  first address: its results are not stored one by one, and the checker's cache (10 minutes) answers the
  addresses already checked.
- **Ownership of writes**: every write of a running job is conditional on the job still belonging to that
  worker; a worker that was only slow, and whose job was given to another, finds out (`JobLost`) and lets go.
- **A clean stop**: on SIGTERM (`docker compose stop`, an update) the worker finishes the record in hand and
  hands the job back to the queue at once, without waiting for the two minutes; the service has a 30-second
  grace period.
- **Is a worker running?** Workers announce themselves in a `workers` collection every 10 seconds. A job
  queued for 15 seconds while no worker has been seen for 30 is reported `stalled`, and the browser says that
  the job worker is not running instead of waiting in silence; `GET /portal/healthz` adds `worker`
  (`ok` or `unavailable`), and the installer warns when the worker does not report.
- **Expiry of unfinished jobs**: a queued or running job expires after a day, a safety net for jobs nobody
  will finish.

### 3.4 Sign-in throttling and caches

- Each failed sign-in inserts one document per key (user name, address). A sign-in is refused while either
  key has five failures inside 15 minutes; a successful sign-in deletes the failures of both keys. The rule
  and the 429 answer are unchanged; the state is now common to every replica.
- The link checker reads and writes `linkcheck_cache` (10 minutes). `LAST_FULL_CHECK` moves to `settings`.

### 3.5 Journal retention

| Variable | Default | Actions |
|---|---|---|
| `PORTAL_JOURNAL_SESSION_DAYS` | 180 | `login`, `login-failed`, `logout` |
| `PORTAL_JOURNAL_RECORD_DAYS` | 0 (kept for ever) | `create`, `update`, `delete`, `import` |
| `PORTAL_JOURNAL_ADMIN_DAYS` | 0 (kept for ever) | `password-change`, `user-create`, `user-update`, `user-reset`, `user-remove`, `export` |

An event is kept for the days of its category counted from the end of the day (UTC) it was made:
`expiresAt` = that midnight + the days, or no `expiresAt` when the value is 0; MongoDB's TTL monitor deletes
it after that time (it runs about once a minute). Whole days keep the rule easy to state and let the portal,
when a value changes, recalculate `expiresAt` of that category at start-up with one update per day of the
journal (under a lock, so replicas do it once). The daily backup keeps what expires
for its own retention (`RETENTION_DAYS`, 14 days by default). A record's history lives in the journal, so a
limit on `PORTAL_JOURNAL_RECORD_DAYS` also limits how far back a record can be restored; the configuration
documents say so.

### 3.6 Migration of existing installations

At start-up, before serving requests, the portal (one process at a time, under a lock document in `settings`):
1. for each of `users.json`, `records-meta.json`, `journal.jsonl` that exists **and** whose collection is
   empty, imports its contents (users as they are, including roles from before roles existed; journal events
   with their dates and categories);
2. renames each imported file to `*.migrated`, keeping it in the volume;
3. writes the counts to `settings.migration` and to the log.

The import is idempotent: a file is read only into an empty collection, and a file already renamed is not
read again. The first user from `PORTAL_ADMIN_*` is still created when the users collection is empty after
the migration. Sessions signed with an old `secret.key` stay valid while that key is the one in use; the
installer copies nothing out of the volume, so when it first writes `PORTAL_SECRET_KEY` every user signs
in once more.

### 3.7 Backup and restore

- `scripts/resolver-backup.sh` already dumps every database as root, so `resolver_portal` is included with
  no change. The volume archive stays while the volume exists (the `*.migrated` files and the fallback key).
- A restore with `mongorestore` brings back `resolver_portal`; `portal-db-init` recreates or updates the
  user at the next start, so a restore needs no extra step. The restore section of the
  [extensions documentation](../extensions/README.md) is updated in step 2.

### 3.8 Replicas (step 4)

- The portal, the worker, `web-service` and `data-entry-service` hold no state of their own after step 3.
- Compose's `deploy.replicas` (or `docker compose up --scale`) needs the fixed `container_name` lines removed
  from those services: a **deliberate change to official code**, recorded in the changelog.
- nginx resolves a service name to every replica's address when it starts and spreads requests among
  them; `depends_on … restart: true` already restarts the proxy when a service behind it is recreated.
- **To settle with the owner at step 4**: whether `web-service` and `data-entry-service` move from Flask's
  built-in server to gunicorn (also a deliberate change to official code), and the default number of
  replicas of each service.

**As implemented in step 4** (the owner's choices, all as recommended, and what the implementation found):
- **Container names**: removed from the three replicable services that had one (`web-service`,
  `data-entry-service`, `portal-service`; `portal-worker` never had one). `database-service` and
  `frontend-proxy-service` cannot be replicated (one MongoDB; the proxy publishes port 8080) and keep their
  official names, the smallest change to official code. Scripts and documents already used service names
  (`docker compose exec|logs <service>`, which act on the first replica or on all of them).
- **Replica counts in `.env`** (`WEB_SERVICE_REPLICAS`, `DATA_ENTRY_SERVICE_REPLICAS`,
  `PORTAL_SERVICE_REPLICAS`, `PORTAL_WORKER_REPLICAS`; Compose's `deploy.replicas`, default 1), because
  `docker compose up --scale` is forgotten at the next `docker compose up` — every update. The installer
  writes the four keys (not asked: 1, the environment or the existing `.env`; 1 to 20).
- **gunicorn in every web service**: `web-service` and `data-entry-service` leave Flask's built-in server for
  gunicorn (deliberate change to the official images, `gunicorn` added to their requirements); the
  application factory is loaded directly (`__init__:create_app()`) so that `main.py`'s own SIGTERM handler
  does not replace gunicorn's; `python -m main` still starts the built-in server for development. The
  portal moves from one process to `WEB_CONCURRENCY`. Each image sets `WEB_CONCURRENCY=2`, which
  `docker-compose.yml` takes from `WEB_SERVICE_PROCESSES`, `DATA_ENTRY_SERVICE_PROCESSES` and
  `PORTAL_SERVICE_PROCESSES`; eight threads per process; `--graceful-timeout 8` so that requests in hand
  finish inside Docker's 10-second stop period; gunicorn 26's control socket is turned off (unused, and it
  would be written to the home folder of the image's user); request lines go to the log, as the built-in
  server's did.
- **The proxy finds replicas by itself**: section 3.8 assumed nginx's start-up lookup and the restart by
  `depends_on … restart: true`; that sees only the replicas that existed when nginx started and misses any
  added later. Instead every upstream is a block with `server <service>:<port> resolve` in a shared `zone`,
  and `resolver 127.0.0.11 valid=10s` asks Docker's DNS again every 10 seconds. nginx shares requests among
  the replicas in turn, goes on to another when one refuses the connection, starts even while a service is
  down, and no longer needs restarting when a service is recreated (the `restart: true` lines are gone; the
  installer's one-off proxy restart stays as a safety net). `resolve` in upstream blocks needs open-source
  nginx 1.27.3 or later, so the proxy image moves from `nginx:1.25.1-alpine` to `nginx:1.30-alpine`, the
  stable branch, which also brings the security releases since 2023 (deliberate change to the official
  image). The URI handling of decision 7 is unchanged: `proxy_pass` still names an upstream block, not a
  variable.
- **The fallback session key under concurrent starts**: with several gunicorn processes, two of them could
  create `secret.key` at the same moment and one read the file before the other had written it, signing
  sessions with an empty key. `_secret_key()` now writes the key to a file of its own and links it to the
  final name (only the first link succeeds); an empty key file stops the portal with a message. Replicas on
  one host share the key through the volume; on several hosts `PORTAL_SECRET_KEY` is required, as decided.
- **CI**: the jobs `e2e` and `install` become required; `database` stays informative. The proxy test needs
  nginx 1.27.3 or later, so its job installs nginx 1.30.5 from nginx.org (Ubuntu 24.04 ships 1.24).

## 4. Options considered

| Point | Chosen | Not chosen |
|---|---|---|
| Database and access | own database and least-privilege user | collections `portal_*` in `resolver_ce` (mixes with the official collections); the root `MONGO_URI` (full access for the portal) |
| Background jobs | job collection + worker container | Redis with RQ or Celery (one more service to install, secure and back up); threads in the portal with the state in MongoDB (a job dies with its replica) |
| Throttling and caches | MongoDB with TTL indexes | throttling only in MongoDB (previews would need sticky sessions); everything in memory (each replica its own lockout) |
| Session key | `PORTAL_SECRET_KEY` in `.env` | stored in MongoDB (the key would sit in the database dump); a file in a shared volume (a volume kept only for that) |
| Journal retention | by age, per category, TTL | by size (could delete the history of records that never change); none |
| Migration | automatic at start-up | a command run by the operator or the installer (one more step to remember) |
| Tests | `mongomock` + a real `mongo:7` job in CI | `mongomock` only (TTL and permissions never tested before staging); a real MongoDB only (the development sandbox cannot run one) |
| Delivery | four steps | two larger steps |

## 5. Consequences

Better:
- any service can run as several replicas; a restart no longer loses imports or link checks;
- one sign-in lockout for the whole installation;
- history and audit queries use indexes instead of reading a file;
- the journal stops growing without limit;
- tenants (2.4), the resolution log (4.1) and the load test (7.4) have a place for shared state.

Worse, and how it is contained:
- the portal now holds database credentials: a user limited to `resolver_portal`, never root;
- more moving parts (`portal-db-init`, `portal-worker`): both use images the installation already builds;
- the worker polls MongoDB once a second when idle: one indexed query, negligible;
- `mongomock` is not MongoDB: the CI job against a real `mongo:7` covers TTL indexes, the user's
  privileges, the migration and worker processes sharing the queue; it is informative until it has proved
  stable. The development sandbox cannot run MongoDB, so that job's first real result comes from GitHub
  Actions.
